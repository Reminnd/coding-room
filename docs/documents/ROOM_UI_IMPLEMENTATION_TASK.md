## Goal and background

Deliver a working local Room UI backed by the existing SQLite RoomService, runner and GitController, ready to open in Codex's in-app browser. There is currently only an MCP and CLI product surface. Build the actual complete user workflows, not a static dashboard or generic JSON dump.

## Requirements and architecture decisions

1. Add a local HTTP UI entry (`npm run room:ui -- ...`) binding 127.0.0.1 only. Reuse the current Room database and RoomService command authority, snapshots, lifecycle errors and GitController. Keep existing MCP/CLI APIs unchanged. It is acceptable to mount/reuse MCP participant routes alongside the UI. No separate workflow database, invented states or bypassing authority.
2. Multiple project registry persisted locally (UI configuration only). Add/select projects with absolute project/database paths and room/control participant identity, including reading existing `.agent-room/runtime.json`. Missing configuration gets a clear setup flow; never silently create, migrate, overwrite or replace a user's database. A deliberate create-room flow may create a fresh database. Expose runtime configuration errors visibly.
3. Simplified Chinese polished compact workbench: sidebar with project picker, overview, plans/tasks, executions, Questions, Reviews, Git, history and settings; content header with connection status, refresh and VS Code. Light/dark/system themes persisted; usable at narrow panel widths and normal desktop sizes. Semantic accessible controls, loading/empty/error states; no fake activity, hardcoded project statistics or placeholder buttons.
4. Overview derives status counts and actionable pending items from snapshots. Plan/Task view shows the actual DAG with dependency edges, status and node details. Provide creation/editing inputs for Plans, revisions and Task Contracts (structured primary fields and a clearly labeled advanced JSON editor for complex protocol objects), approval/reconcile actions and readable scope/acceptance details. IDs/timestamps can be generated by UI when appropriate, but no implicit approval.
5. Execution view lists real Runs/attempts, progress and events; start an existing ready Run using the existing one-shot Claude runner and actual MCP binding, cancel/retry/guidance through service authority. Display durable state and surfaced process errors. Don't hold HTTP request until a long run finishes. Avoid duplicate launches while an attempt is active. Don't add a fake Codex adapter: native Codex repository development remains Local Bridge (controller integrates separately).
6. Questions have readable question/options/context and actual answer submission including contract-change flag. Reviews show findings and support review submission, accept, and Fix Task preparation/submission per protocol. Clear disabled reasons for illegal operations; errors must leave forms usable.
7. Git page shows actual current branch/status and worktrees, Room GitActions preview/approval/execute/reconcile and results. Use GitController rather than arbitrary shell commands. VS Code button launches the selected project's or run's actual worktree using argument arrays or a correct vscode:// link (handle spaces). Native Codex review can be a link when supported; don't invent a custom native panel API.
8. History shows/filter events and terminal work with export of an archive JSON artifact without deleting SQLite data. Settings supports participant/role management through existing application methods plus theme/project configuration. Poll/reconnect automatically; ensure polling does not erase focused/dirty forms, change selected records, or hide server errors.
9. Local operation only, no new authentication/accounts/cloud services. The user's latest amendment requires a React + TypeScript frontend. Use a small Vite React frontend with its own package/lock/tsconfig under `frontend/`, served by the same local HTTP server in production. Keep server/actions/components organized by actual purpose. Validate action input via existing schemas; explicit project selection fixes command routing. UI must never let a caller-provided actor override configured participant.
10. The HTTP API is the single application entry for React, a `taskctl` CLI and a Codex Skill. Add `tools/taskctl.mjs` using Node fetch and argument arrays; commands for projects, state, actions, events/export and opening VS Code, with readable output and `--json`. Add an API reference with examples in ROOM_UI.md. Controller separately supplies the Skill, CDP injection and Tauri wrapper; do not implement those in this task. Keep the API usable without browser-only authority tokens while retaining loopback/origin constraints appropriate to a local cooperating operator.
