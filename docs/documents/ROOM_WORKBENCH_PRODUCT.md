## 1. 产品定位与三个概念

Room 帮用户把一项开发需求从讨论带到可验收的代码交付。用户在同一个任务里选择材料、看方案、回答问题、观察执行、检查测试与变更，最后决定是否接受和提交代码。

| 概念 | 用户看到的名称 | 解决的问题 | 输出 |
|---|---|---|---|
| SDD | 规格模式（SDD） | 先明确要做什么、如何划分模块，再实施 | 规格、技术设计、任务及验收条件 |
| Task-driven | 任务模式 | 把一个边界较清楚的问题快速拆成执行步骤 | 原生 Codex Plan、步骤及验收条件 |
| Test-driven development | 测试驱动（TDD） | 用先失败再通过的测试指导每个行为改动 | Red/Green 证据、必要重构与回归结果 |

SDD 和任务模式是创建任务时的两个入口；测试驱动是它们共用的实施方式，不设第三个互斥开发入口。SDD 同样可以先写测试，任务模式同样需要说明目标和验收条件。

建议代码行为变更默认启用测试驱动；纯文档/文案、没有可用自动测试入口的任务可以使用普通验证，并说明验证方式。用户不需要为每一轮 Red/Green 点击批准。

## 2. 来源规则

| 来源类型 | 用途 | 在方案中的呈现 |
|---|---|---|
| 成熟 GitHub 仓库 | 参考实现与模块组织 | 参考了哪个模块、采用什么、哪些部分不适用 |
| 模块代码文件 | 参考实现与模块组织 | 相关接口、职责、依赖和可复用做法 |
| 外部项目开发文档 | 参考实现与模块组织 | 设计取舍、模块关系和实现路径 |
| 本项目开发文档 | 确定需求、接口与约束 | 必须满足的行为、接口定义、范围及约束 |

当前项目代码也用于核对既有实现事实；它与本项目文档不一致时，显式指出差异，不能默默把代码或外部参考提升为新的需求。用户本次明确要求仍优先于旧文档。

上传/选择资料时必须标明属于“本项目”还是“外部参考”，系统可以建议分类，用户可修正。不按文件扩展名猜测权威级别。资料不是越多越好：只读取任务实际相关的部分；不要求每项任务都填齐四类来源。

项目资料页保存可复用来源；每项任务明确选中本次使用的来源。计划记录引用路径/链接及使用版本或读取时间，方便回看依据，不新增内容指纹。

### 视觉与窗口规范

以下为本次修正补齐的设计基准，不是已经通过截图验收的结果。以任务可读性为主，不增加营销 Hero、展示字体或装饰统计。

| 项目 | 规范 |
|---|---|
| 字体 | 使用本机 `Segoe UI`、`Microsoft YaHei UI`、sans-serif；代码用 `Cascadia Mono`、`Consolas`、monospace；不依赖在线字体 |
| 字号 | 页面标题 20/28 px，区块标题 16/24 px，正文与控件 14/22 px，辅助信息 12/18 px；主要任务内容不使用辅助字号 |
| 间距与形状 | 4/8/12/16/24/32 px 间距；内容内边距 24 px，窄窗口 16 px；控件圆角 6 px，弹窗 10 px |
| 控件 | 常规按钮与输入框高 36 px，多行输入框按内容扩展；图标按钮有可访问名称，焦点环 2 px，不以颜色单独表达状态 |
| 浅色 tokens | background `#F8FAFC`、surface `#FFFFFF`、text `#0F172A`、muted-text `#475569`、border `#CBD5E1`、action/focus `#1D4ED8`、on-action `#FFFFFF` |
| 深色 tokens | background `#0F172A`、surface `#1E293B`、text `#F8FAFC`、muted-text `#CBD5E1`、border `#64748B`、action/focus `#93C5FD`、on-action `#0F172A` |
| 状态文本 | 浅色 success `#166534`、warning `#92400E`、error `#B91C1C`；深色分别为 `#86EFAC`、`#FCD34D`、`#FCA5A5`；同时显示状态文字，预期 Red 明确写“预期失败” |
| 动效 | 只用于操作反馈，约 120–180 ms；尊重 reduced-motion，不让装饰动画阻碍阅读和操作 |

布局按 Renderer 可用 CSS 宽度判断：≥1280 px 显示 220 px 左栏与 300 px 右栏；1000–1279 px 自动收起右栏，左栏缩至 200 px。缩放后可用宽度低于 1000 px 时，左栏改为标题栏“导航”按钮打开的抽屉，右栏保持抽屉；两者不同时覆盖内容。六个页签允许横向滚动，选中项滚入可见区。Diff 默认在窄窗口使用统一视图，代码区可横向滚动，页面整体不横向溢出。

抽屉/弹窗打开后将焦点移入，Esc 关闭并返回触发按钮；未保存编辑先走保存/放弃/继续编辑处理。主要操作所在底栏不得遮挡最后一段内容或键盘焦点。实现前用任务列表、任务详情、新任务表单验证这套规范；覆盖 1440×900、1000×700、Windows 125%/150% 缩放及两种主题，检查实际文字/控件对比度与溢出，不把设计值当作实测结果。

左栏负责定位项目中的任务；顶部六个页签只改变同一任务的内容视图。流程条显示进度、允许查看历史，不允许通过点击某个阶段直接改变任务状态。主要操作放在内容区右下角或对应决策卡片中；同一操作不在多个地方同时出现可点击副本。

## 4. 首次打开与项目管理

没有项目时主内容区显示欢迎页：中央“打开项目文件夹”，下方最近项目列表。选中目录后显示项目名称、路径、Git 状态、已有 Room 及 Agent 检测结果。

| 按钮 | 位置 | 点击结果与前置条件 |
|---|---|---|
| 打开项目文件夹 | 欢迎页中央 | 原生目录选择；取消选择保持原页 |
| 打开 | 最近项目卡片右侧 | 打开该项目；路径不存在时呈现“重新定位” |
| 使用已有 Room | 检测结果卡片右下 | 已存在有效绑定时导入并进入任务列表 |
| 为此项目创建 Room | 无绑定的检测卡片右下 | 显示数据位置，用户确认后创建；不覆盖已有数据库 |
| 重新选择 | 检测结果卡片左下 | 返回目录选择 |
| 配置 Agent | Agent 不可用提示内 | 打开设置；仍可浏览已有项目资料和记录 |

正常用户不输入数据库路径、端口或 Participant ID；已有异常配置才在“详细信息”展示诊断。空任务列表显示“暂无任务，请使用导航中的‘＋新建任务’”，不增加重复按钮或假的示例任务。新建能力尚未交付的阶段不展示可点击入口，空状态如实说明当前只支持浏览已有任务。

项目有未提交代码时可以讨论和规划；执行前在工作区准备卡片说明受影响文件及处理方式。不得为启动任务自动丢弃用户改动。

任务列表页顶部是任务标题搜索框，右侧为状态筛选；新建任务统一使用导航入口。每行显示标题、开发入口、验证方式、当前状态和最近活动；点击标题打开该任务，右侧“…”菜单提供重命名和适用的归档/取消操作。列表不堆叠 Run/Attempt ID。搜索无结果时保留查询并提供“清除筛选”，不误报项目没有任务。

列表上下文按项目保存，进入详情及切换项目不重置查询和筛选。返回时若原任务行已不符合筛选，保留筛选，将焦点移到列表标题并解释该任务已移出当前结果；不默默清除查询。由待办直达且没有历史列表位置时，返回该项目“全部任务”。离开有未保存输入的页面提供保存、放弃、继续编辑，取消离开保持当前项目与输入。

## 5. 新任务面板

点击“＋新建任务”后，中央显示表单，左栏仍可见；右栏暂收起。

从上到下：

1. **任务标题**：一句话描述；输入框旁“从目标生成”提供建议并填入供用户修改，目标为空时禁用。草稿允许为空；开始讨论前必须为非空白标题，不自动覆盖用户已填写的标题。
2. **希望完成什么**：多行输入目标、现象或需求；草稿允许不完整，开始讨论前必填。
3. **开发入口**：分段按钮“规格模式（SDD） / 任务模式”。任务模式说明“使用 Codex 原生 Plan”。
4. **验证方式**：默认“测试驱动”，可选择“普通验证”；旁边“了解 TDD”展开本文第 10 节的简短例子。
5. **本次资料**：已选来源卡片、“从项目资料选择”“添加参考”。本项目规范可预选，外部参考由用户选择。
6. **执行配置**：折叠显示规划 Agent、执行 Agent、实际可用模型和工作目录；默认继承项目设置。不能显示不可用 provider。

| 按钮 | 位置 | 作用与下一步 |
|---|---|---|
| 保存草稿 | 表单底部左侧 | 保存不完整输入，回任务列表；无标题时列表显示“未命名草稿”，不是用占位文字填充真实标题；不调用 Agent |
| 开始讨论 | 表单底部右侧，主要按钮 | 校验非空白标题、目标和 Agent 状态；不通过时保留输入，在字段旁解释并聚焦首个错误；通过后创建/恢复讨论，进入“对话”页签 |
| 从项目资料选择 | 资料区域 | 打开已有来源勾选抽屉；确认后只关联当前任务 |
| 添加参考 | 资料区域 | 打开资料弹窗；保存后关联当前任务 |
| 取消 | 表单底部次要按钮 | 输入未保存时提供保存草稿/放弃编辑选择 |

开发入口与验证方式在方案确认前可修改；执行开始后修改需停止当前执行并修订方案，不能在运行中偷换目标。

## 6. 资料页与来源弹窗

项目资料页中央为“本项目文档 / 外部参考”两个分组。代码文件可以按来源归属放入相应分组，但用途显示为“实现与模块参考”。顶部有文本搜索，右侧“添加资料”。资料详情显示位置、归属、用途、摘要与最近读取结果。

添加资料弹窗提供“GitHub 仓库”“文档”“代码文件”三种输入类型；另有“本项目/外部参考”归属选择。仓库输入 URL 与可选模块路径；文档选择文件或填写 URL；代码选择文件/目录。外部文档卡片明确标为参考，本项目文档明确标为需求/接口/约束来源。

| 按钮 | 位置 | 作用 |
|---|---|---|
| 添加资料 | 资料页右上角 | 打开来源弹窗 |
| 浏览文件/目录 | 弹窗路径输入框右侧 | 打开系统选择器 |
| 保存资料 | 弹窗右下角 | 保存来源引用与归属，不自动复制整个仓库或执行其中代码 |
| 打开原文 | 资料详情顶部 | 打开本地文件或外部链接 |
| 用于当前任务 | 资料详情右下角 | 将来源关联当前任务；来源尚未读取时标为待读取 |
| 更正分类 | 资料卡片菜单 | 修正本项目/外部参考及用途 |
| 从任务移除 | 任务资料卡片菜单 | 只移除当前任务关联，不删除原文件 |
| 从资料库移除 | 项目资料卡片菜单 | 移除项目引用，保留任务历史中的来源记录和原文件 |

读取失败时显示具体来源和原因，卡片内提供“重试读取/移除关联”。关键本项目规范无法读取时方案呈现缺口；不声称已经遵循。

## 7. 对话与两种规划路径

用户已确认：普通规划使用现有账号的 ChatGPT 普通 Chat，讨论界面保持在 Room，由内置页面桥接搬运与官方网页之间的消息。[ADR-0007 §3.3](./ADR/0007-electron-task-workbench.md#33-规划调用更正2026-10-12用户明确要求) 定义调用边界。SDD 对话页顶部标记 ChatGPT 普通聊天，中间为可独立滚动的消息列表，底部为 Room 输入框。官方网页通常隐藏，登录、上传文件或处理异常时才在 Electron 内显示。

| SDD 按钮 | 位置 | 作用与后续 |
|---|---|---|
| 发送 | Room 输入框右下角 | 将当前消息与任务资料送入关联网页；发送前失败留下的 Room 草稿可直接重试，修改消息时替换旧草稿；网页出现实际用户消息后清空 Room 草稿 |
| 停止生成 | 回复期间替换“发送” | 操作该任务网页的停止按钮 |
| 采用此方案 | 未自动保存的 ChatGPT 回复下方 | 手动保存选定回复为方案草稿；不启动执行 |
| 查看已保存方案 | 已自动保存的回复下方 | 打开版本化方案草稿，进入审阅与执行前确认 |
| 提交答案并继续 | “需要你明确需求”弹窗底部 | 各问题选择推荐/其他选项或填写自定义答案后，将答案发回同一 Chat |
| 回答需求问题 | 暂时关闭弹窗后，讨论页状态下方 | 重新打开尚未回答的需求问题 |
| 打开网页 / 登录 | 讨论页顶部右侧 | 显示任务关联网页，供登录、上传或处理异常 |
| 重新加载 | 网页窗口顶部 | 核对发送结果后重新加载页面；不自动重发消息 |
| 保存页面诊断 | 网页窗口顶部 | 输入框识别异常时保存控件属性到本地日志目录；不采集聊天正文、输入值或 cookies |
| 返回 Room | 网页窗口顶部最右侧 | 隐藏网页窗口，继续在 Room 讨论；网页保持连接 |
| 查看方案 | 讨论页顶部右侧 | 进入方案审阅与执行前确认 |

ChatGPT 网页与 Room 为独立窗口，各自最小化和恢复；点击“返回 Room”隐藏网页，退出应用才统一关闭。

2026-10-12 用户确认补充：普通 Chat 按 Skill 的澄清方法讨论，Room 展示选择框，不要求网页实际调用本地 Skill。讨论提示使用 grilling 的逐轮决策方法：前提已明确的问题先问，依赖未决答案的问题后问，推荐选项说明取舍并等待用户决定，每轮最多三问。网页以 `room_questions` 返回结构化问题；Room 自动弹窗，保留自定义答案及暂时关闭入口。

讨论页顶部状态区持续显示发送确认、思考或准备回复、正在输出、方案保存结果及停止状态。回复结束且文本稳定后，含有效 `room_task` 的完整方案自动保存为草稿并显示版本；不跳转打断讨论、不授权执行。相同回复不重复保存，刷新不覆盖人工编辑。未识别到结构化方案时明确提示并保留手动采用；主动停止的部分回复不自动保存。

原生 Plan 的“对话”页签中央显示用户与 Codex 的消息；来源读取、方案生成、提问以可展开卡片呈现。底部固定输入框，右下角“发送”。Agent 正在输出时同一位置显示“停止生成”。右栏显示目标、已用资料与未解决事项。

普通规划使用 Chat，只有采用 Codex 原生 Plan 的路径调用 Codex；执行另行确认。SDD“开始讨论”进入 Room 讨论界面，“补全技术设计与任务”通过网页桥接发送补全请求，不调用 App Server。官方页面加载失败时在 Room 显示原因，任务与草稿保留。以下原生 Plan 问题卡片沿用原接口；SDD 使用上述结构化澄清弹窗，回答仍发送为普通聊天消息。

| 按钮 | 位置 | 作用 | 下一环节 |
|---|---|---|---|
| 发送 | 对话输入框右侧 | 发送目标、回答或补充；普通聊天不授权执行 | 继续讨论 |
| 停止生成 | 输出期间的输入框右侧 | 中断当前规划 turn，保留已有内容 | 继续编辑/重新发送 |
| 回答问题 | 对话中的问题卡片 | 选择建议答案或输入自定义答案 | 继续规划 |
| 生成计划 | 任务模式讨论后的卡片右下角 | 使用原生 Plan 形成精简步骤与验收 | 方案页：计划 |
| 查看方案 | 已生成方案消息卡片 | 打开同一任务的“方案”页签 | 方案审阅 |

**SDD 路径**：通过 Chat 阅读来源 → 澄清需求 → 规格与场景 → 技术设计/模块组织 → 实施任务与测试场景。用户可以分步查看编辑，但不要求每一步都做正式审批；完整方案确认是执行前的关键决定。切换为 SDD 后的新讨论使用 Chat；已有原生 Plan 历史保持其真实来源，不能改标成 Chat 历史。

**任务模式路径**：阅读相关资料 → 原生 Plan 澄清 → 精简步骤、影响范围和验收场景。边界复杂时用户可“切换为 SDD”，沿用已有资料和讨论，增加必要规格；原计划保留为历史草稿。

原生 Plan 不可用时显示能力缺失与配置入口，不能把普通对话输出换个标题作为原生 Plan。

方案页上方显示版本及“草稿/待确认/已确认”标签。SDD 子页为“规格 / 技术设计 / 实施任务”；任务模式直接显示精简计划。两者都有目标、范围、不做什么、验收条件、测试策略和参考来源。实施任务逐项列出模块、依赖和验收，不向用户暴露需要手填的 DAG JSON。

| 按钮 | 位置 | 作用与条件 | 下一环节 |
|---|---|---|---|
| 编辑 | 方案标题右侧 | 编辑当前草稿；已确认方案产生新修订，保留旧版本 | 方案修改 |
| 保存修改 | 编辑区右下角 | 保存用户修改；不自动批准 | 待确认 |

执行确认卡片显示：当前方案版本、将执行的任务、涉及模块/文件范围、验证方式、执行 Agent、实际工作目录、Git 操作是否包含在本次授权内。右下角“开始执行”，左下角“返回修改”。这一个确认动作批准本轮可见范围内的执行；每条测试和每个步骤不重复确认。

确认后更改方案，旧确认不能自动覆盖新内容；计划未变化的读取或页面切换不要求重新确认。

## 9. 执行页、提问与恢复

执行页左侧为步骤列表，中央为当前步骤摘要与事件，底部可展开完整日志。任务顶部显示“正在执行哪一步”，不显示没有实际计量依据的完成百分比。测试驱动任务在步骤卡片内显示当前 Red/Green/Refactor 阶段。

| 按钮 | 位置 | 作用与条件 |
|---|---|---|
| 停止执行 | 执行页右上角，执行中可用 | 请求停止，先显示“停止中”，收到真实终态后才显示“已停止”；保留代码改动 |
| 补充说明 | 当前步骤卡片下方 | 显示“下一执行步骤读取”；不假装现有 Claude Runner 能实时 steer |
| 查看完整日志 | 当前步骤卡片底部 | 展开原始输出、时间和命令 |
| 查看测试 | 测试事件卡片右侧 | 切换测试页并定位对应运行 |
| 查看变更 | 文件变更摘要右侧 | 切换变更页并定位文件 |
| 提交答案并继续 | 待回答卡片右下角 | 用户回答后按执行器真实能力恢复；旧执行尚未停止时不能启动重叠执行 |
| 修改方案 | 问题涉及范围变更时的卡片 | 回方案页生成新修订，执行继续保持停止 |
| 查看错误 | 失败卡片中 | 展开失败步骤、错误原因和已有改动 |
| 重试失败步骤 | 失败卡片右下角 | 重新核对当前状态后重试，保留已完成步骤，不盲目重放整个任务 |
| 继续任务 | 停止/重启后的任务卡片 | 恢复前展示当前工作区与执行情况；无法确定旧执行状态时先定位状态，不启动第二份 |

“停止执行”是中断进程，“取消任务”是用户放弃本任务；两者均不自动撤销代码。取消任务位于任务标题“…”菜单，活动执行需先停止；已接受任务使用归档，不回写成取消。

退出应用且有活动任务时，弹窗提供“继续后台运行”“停止任务后退出”“返回”。服务异常和 TDD 中预期的 Red 失败是不同状态：前者显示运行故障，后者显示“已证明预期行为尚未实现”。

## 10. TDD：操作流程与产品呈现

TDD 是 Test-Driven Development，中文为测试驱动开发。每次选一个具体行为，先写一个会验证它的自动测试，运行看到这个行为尚未实现，再写代码让测试通过。测试也帮助之后修改代码时发现回归。

普通“写完代码再测”和 TDD 都会运行测试；区别在于 TDD 的测试先于对应行为实现，并参与决定代码应做什么。测试通过只证明被断言的场景，仍需要正确的需求、Review 和必要的端到端验收。

### 10.1 一个完整例子

需求：“任务标题为空或只有空格时，不能开始讨论；保存草稿仍允许不完整输入。”本例校验讨论启动边界，不用于拒绝草稿保存。

| 步骤 | Agent 操作 | 用户看见的证据 |
|---|---|---|
| 确定行为 | 把需求写成场景：空白标题不能开始讨论；有效标题与目标可进入讨论；不完整输入可保存草稿 | 方案中的验收与测试场景 |
| Red | 先写空白标题启动讨论的测试，运行它；当前实现仍接受空白标题 | 该用例失败，实际结果与预期不符 |
| Green | 添加必要的标题校验，重跑同一用例 | 同一测试通过，显示实际代码变更 |
| 回归 | 检查有效标题与目标仍可启动讨论、不完整草稿仍可保存，以及受影响的已有行为 | 正常路径与相关测试结果 |
| Refactor | 如有重复校验逻辑则在不改行为的前提下整理；无必要则跳过 | 有整理时显示相关变更及再次通过的测试 |
| 下一行为 | 再处理另一个验收场景 | 新的一轮，直到本次范围完成 |

一个用于理解的最小 TypeScript 例子：

```ts
// Existing behavior, used to demonstrate the missing validation.
export function isTaskTitleValid(title: string): boolean {
  return true;
}
```

先写测试：

```ts
import assert from 'node:assert/strict';
import test from 'node:test';
import { isTaskTitleValid } from './task-title.ts';

test('rejects a whitespace-only task title', () => {
  assert.equal(isTaskTitleValid('   '), false);
});
```

运行得到 `true !== false` 是 Red：测试可以正常运行，但目标行为缺失。然后实现：

```ts
export function isTaskTitleValid(title: string): boolean {
  return title.trim().length > 0;
}
```

重跑同一测试通过是 Green。这只是原理示例；实际产品还应验证点击“开始讨论”及调用讨论启动接口时确实执行了校验，并证明保存草稿不被该校验阻断，不能只测试未被调用的 helper。

模块找不到、测试工具没装、服务连不上都不是有效的 Red。测试一开始就通过时先判断行为是否已经存在，不故意破坏实现来制造失败。发现测试写错可以修正测试并说明依据；不能为了通过而删除需求所要求的断言。

### 10.2 用户与 Agent 分工

用户负责确认业务行为、边界和验收，必要时回答歧义问题。Agent 负责写测试、运行测试、实现代码和记录证据；应用展示实际命令结果。正常 Red → Green 不暂停等待用户操作；需求不清楚、环境不可用或实现需要扩大范围时才形成待办。

### 10.3 测试页布局和按钮

上方显示当前实际测试结果与最近运行时间，中部按行为分组，下方为所选用例的历史证据：`Red 预期失败 → Green 通过 → Refactor 后通过/无需重构`。旧失败证据保留但不冒充当前失败。

| 按钮/控件 | 位置 | 作用与条件 |
|---|---|---|
| 当前结果 / TDD 过程 | 测试页顶部 | 切换最新结果与先失败后通过的历史 |
| 全部 / 失败 / 通过 | 用例列表上方 | 筛选实际运行的用例 |
| 查看命令与输出 | 用例详情底部 | 展示命令、目录、退出码、失败断言与输出 |
| 查看关联改动 | 用例详情右侧 | 定位对应测试或实现文件的 Diff |
| 重跑失败测试 | 测试页右上角 | 复用该任务已确认的测试命令；执行器正运行冲突命令时禁用 |
| 运行本任务验证 | 测试页右上角次要按钮 | 运行计划确定的验证范围；结果更新当前证据，不创建新业务需求 |

没有测试结果时显示“尚未运行”；普通验证任务展示实际验证方式，不显示假的 Red/Green。一次测试退出码为零但没有执行目标用例，不能计为对应行为已验证。

## 11. 变更页与审阅

“变更”页左侧为文件列表，中央为只读 Diff，顶部显示新增/修改/删除摘要。文件名称来自实际 Git。用户可以在外部编辑器继续阅读；不建设完整浏览器 IDE。

| 按钮 | 位置 | 作用 |
|---|---|---|
| 文件条目 | 变更页左侧 | 显示该文件的实际 Diff |
| 并排 / 统一 | Diff 顶部 | 切换 Diff 展示方式 |
| 在编辑器打开 | Diff 顶部右侧 | 打开当前项目或所选文件 |
| 针对此处提意见 | Diff 行/选区菜单 | 将位置和意见带到任务对话；记录意见不直接授权修改 |
| 重新读取变更 | 文件列表上方 | 外部改动后刷新 Git 事实，并提示旧 Review 是否需要更新 |

“验收”页展示目标、验收条件、变更摘要、测试、Review findings 和未决问题。执行完成不等于已接受。Reviewer 可以自动开始审阅已完成的候选；未产生真实结果前显示“审阅中”，失败提供“重试审阅”。

| 按钮 | 位置 | 作用与条件 | 下一环节 |
|---|---|---|---|
| 查看证据 | 每条验收条件/发现右侧 | 打开对应测试、文件、日志或来源 | 阅读核对 |

| 确认修复并执行 | 修复方案卡片右下角 | 只执行卡片列出的已确认问题和方案 | 修复循环 |
| 接受本次结果 | 验收页底部右侧 | 必需验证完成且无未解决阻塞时可用；保存用户接受事实 | 已完成/交付 |

## 12. 完成与 Git 交付

接受后任务显示“已完成”，并独立显示“代码未提交/已提交”等实际 Git 状态。接受不隐含 commit、push 或合并。完成页保留方案、测试与 Review。

| 按钮 | 位置 | 作用与条件 |
|---|---|---|
| 提交代码… | 完成页右下角 | 打开 Git preview：实际文件范围、分支和 commit message；由既有 GitController 处理 |
| 确认提交 | Git preview 右下角 | 仅提交预览范围；失败保留状态并显示原因，不清理工作区 |
| 集成到目标分支… | 完成页交付区，仅存在适用 worktree/lineage 时显示 | 预览现有 GitController 支持的 fast-forward 集成，确认后执行；不把不支持的 merge 显示为可用 |
| 新建后续任务 | 完成页左下角 | 引用本任务结果，新建独立需求草稿 |
| 归档任务 | 标题菜单 | 从日常任务列表移至历史，不删除记录或项目文件 |

首版沿用现有 Git 能力，不展示无法兑现的 push、rebase 或任意合并按钮。是否扩展这些能力单独按真实需要决定。

## 13. 待办、历史、设置

### 待我处理

每条卡片显示任务标题、等待原因和等待时间。待确认方案的“查看并确认”打开方案页；待回答的“回答”打开问题卡片；待验收的“查看结果”打开验收页。入口负责定位，最终确认只发生在包含具体内容的页面。处理后根据实际状态移出列表。

跨项目提醒复用项目切换器，不新增通知中心：项目 A 等待用户而当前在项目 B 时，顶栏提示“其他项目有待办”；展开菜单可见 A 的待办数量，点击该数量切换到 A 的待办列表，再选择具体任务。不得未经操作自动切换项目或打断输入。提醒来自已注册项目的实际状态，读取失败显示“状态不可用”，不显示虚假的零待办；确认操作仍在对应项目任务页完成。

### 项目历史

顶部按任务标题/状态/日期筛选；列表点击打开原任务只读结果。右上角“导出记录”导出选中任务的方案、结果和证据引用；导出范围必须说明，不把不包含的完整代码或数据库称为备份。

### 设置

| 设置分组 | 内容 | 按钮与位置 |
|---|---|---|
| 项目 | 名称、路径、数据位置、默认开发入口和验证方式 | 页面底部“保存”；危险操作区“从列表移除项目”，仅移除绑定 |
| Agent | 实际可用的 Codex/Claude、模型、登录/连接情况、规划/执行分配 | 每个 Agent 卡片右侧“检测连接”；支持时显示“登录/重新登录” |
| 执行 | 项目默认工作目录策略、现有权限配置说明 | 页面底部“保存”；任务确认仍显示本次实际配置 |
| 外观 | 系统/浅色/深色、字号 | 选择后即时预览并保存 |
| 关于与诊断 | 应用版本、数据目录、故障信息 | “打开日志目录”“查看更新说明”；首版不假装已有自动更新服务 |

本项目规范仍约束 Agent 的操作。设置不提供“一键跳过所有审批”或凭 UI 显示覆盖后端状态的选项。

## 14. 状态与主要行动

以下是面向用户的展示状态，由实际草稿、规划和执行事实生成；不是要求新增同名 Room protocol state。

| 展示状态 | 页面主行动 | 完成该动作之后 |
|---|---|---|
| 草稿 | 开始讨论 | 讨论中 |
| 讨论中 | 生成规格/生成计划 | 方案草稿；Agent 有问题则等待回答 |
| 方案草稿 | 完善方案/提交修改意见 | 待确认 |
| 待确认 | 检查并执行… | 执行准备，通过后执行中 |
| 执行中 | 查看当前步骤；需要时停止执行 | 待回答、执行失败、已停止或审阅中 |
| 待回答 | 提交答案并继续 | 继续执行；范围变化则回方案 |
| 执行失败/已停止 | 重试失败步骤/继续任务 | 核对恢复条件后执行 |
| 审阅中 | 查看变更与测试 | 待验收或待确认修复 |
| 待验收 | 接受本次结果/提出修改 | 已完成或修复方案 |
| 已完成 | 提交代码/新建后续任务/归档 | Git 交付或历史 |
| 已取消 | 查看保留的变更与记录 | 可以以其为来源新建任务，不自动撤销代码 |

## 15. 两个端到端操作实例

### 任务模式 + TDD：禁止空白标题启动讨论

打开项目 → 左上“＋新建任务” → 填写目标 → 选择“任务模式”，保持“测试驱动” → “开始讨论” → 回答范围问题 → “生成计划” → 方案页“检查并执行…” → 确认卡片“开始执行” → 执行页观察标题测试 Red/Green → 测试页看实际结果 → 变更页检查校验已接入讨论启动路径 → 验收页“接受本次结果” → 按需“提交代码…”。

### SDD + TDD：重构项目任务列表

项目资料添加成熟仓库、参考模块和外部设计文档，并标为参考 → 选择本项目需求文档作为约束 → “＋新建任务”选择 SDD + TDD → 对话澄清任务分组、筛选和状态行为 → “生成规格” → 方案页查看场景并“补全技术设计与任务” → 确认完整方案 → Agent 按模块与依赖执行，每个新增行为走测试驱动 → 实际桌面操作验收布局、键盘操作和空/错状态 → Review 与用户验收 → 提交和归档。

## 16. 产品验收边界

最终验收必须实际走通上述两条路径，并验证项目切换、提问恢复、执行失败、重启恢复、方案修订、真实 Diff/测试/Review 与 Git preview。用户从新建需求到验收不必手填内部 ID 或 JSON；原生 Plan、TDD 证据和后台运行不能由静态展示替代。

按钮必须有真实成功结果、失败反馈及必要的禁用原因。输入未保存时离开有明确处理；键盘可到达主要控件，状态同时有文字，不能只依靠颜色。具体持久化与协议变化在对应实施契约中明确，不通过前端本地状态绕过。
